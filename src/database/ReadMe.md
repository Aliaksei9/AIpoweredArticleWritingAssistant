# Модуль сбора данных и PostgreSQL

Пакет `src.database` содержит интерфейс `BDdataCollection`, реализацию `TGdataCollection` и классы для чтения и записи актуальных статей. PostgreSQL с расширением `pgvector` запускается через Docker Compose. Команды ниже запускаются из корня проекта.

Для каждой статьи хранится один актуальный набор метрик. Повторный сбор обновляет строку по ID статьи и время `collected_at`. История замеров удалена; `init-db` выполняет миграцию к пяти исходным таблицам. `reembed` обрабатывает только актуальные тексты. [Общий контракт обучения и прогноза](../../docs/unified_social_inputs.md).

Файлы модуля: `bd_collection.py` — интерфейс и общие параметры/результаты сбора, `ids_converter.py` — вычисление UUID, `table_classes.py` — работа с таблицами, `model_embedding.py` — векторизация, `topic_detector.py` — выбор категории, `topics.txt` — редактируемый список тем, `resources/telegram/collector.py` — сбор Telegram, `connection.py` — соединение и инициализация БД.

## Расширение источников

Точка входа `__main__.py` только запускает `run_cli()` с подходящим циклом событий.
Код разделён по ответственности:

| Файл | Ответственность |
| --- | --- |
| `cli.py` | Аргументы команд и отдельные обработчики init/reset/reembed/login/update |
| `embeddings.py` | Пересчёт сохранённых векторов настроенной моделью |
| `collection_service.py` | Общий обход ресурсов, прогресс, общий клиент/модель на запуск, отчёт и обработка ошибок |
| `resources/base.py` | Контракт `SourceAdapter`, контекст зависимостей и `SourceRegistry` |
| `resources/telegram/adapter.py` | Ключи Telegram, нормализация адресов, создание/закрытие клиента и `TGdataCollection` |
| `resources/telegram/collector.py` | Получение статей и социальных метрик Telegram, заполнение и обновление БД |
| `resources/__init__.py` | Регистрация доступных источников |
| `bd_collection.py` | `BDdataCollection`, `CollectionOptions`, `CollectionResult` |
| `vector_utils.py` | Общие размерность, проверка и нормализация векторов |

Значения по умолчанию задаются один раз в `bd_collection.py`: `DEFAULT_LIMIT = 1000`,
`MIN_ARTICLE_AGE_DAYS = 2`, `MAX_ARTICLE_AGE_DAYS = 14`. Их используют CLI,
`CollectionOptions` и Telegram-сборщик. Общие `validate_vector()` и
`normalize_vector()` находятся в `vector_utils.py`; детектор и поиск не обращаются
к внутренним методам друг друга. Размер `EMBEDDING_DIMENSIONS` задаётся конфигурацией (по умолчанию 384).

Общий сервис не обращается к полям Telegram. `BDdataCollection.update(resource, limit)`
по-прежнему возвращает количество обработанных статей. Свойство `last_result` возвращает
`CollectionResult`: `processed`, `created`, `updated`, `skipped_by_age`,
`skipped_without_date`, `deleted_expired`, `resource` и `window`. Дополнительные
показатели конкретного API находятся в `details`: для Telegram это
`scanned_messages`, `skipped_incomplete_metrics` и `skipped_unembeddable_text`.
`processed` вычисляется как `created + updated`. `last_result` возвращает независимый
снимок результата, поэтому изменение полученных словарей не меняет состояние сборщика.
Это единственное состояние результата; отдельных полей `last_sync_stats`
и других `last_*` счётчиков нет. Сборщик сбрасывает результат перед каждым ресурсом
и предоставляет актуальные счётчики также после частично завершённого обновления.
Прогресс передаётся через `on_progress(count)`.

Для добавления, например, Habr:

1. Реализовать сборщик `BDdataCollection` с `update` и `last_result`.
2. Создать адаптер `SourceAdapter` в `resources/habr/adapter.py`, указать `code = "HABR"`.
   Метод `open(context)` — асинхронный контекстный менеджер: он создаёт клиент API,
   передаёт сборщику `context.connection`, `context.embedder`, `context.options`
   и закрывает клиент при завершении или ошибке. SDK источника импортируется внутри метода.
3. Если нужны особые адреса/настройки/вход, переопределить `normalize_resource`,
   `validate_configuration` и `login`. В базовом адаптере адрес просто очищается от
   пробелов; символ `@` добавляет только Telegram-адаптер.
4. Импортировать новый адаптер и добавить `registry.register(HabrSource())` в
   `resources/__init__.py`. Менять точку входа, обработчик update и общий сервис не требуется.

После регистрации источник автоматически появляется в `--source`. Если `--source`
не указан, последовательно запускаются **все зарегистрированные источники** в порядке
регистрации. Если указан, запускается только выбранный источник. Сейчас зарегистрирован
только `TG`, поэтому прежние команды продолжают собирать Telegram:

```powershell
.\.venv312\Scripts\python.exe -m src.database update jeteed --limit 1000
.\.venv312\Scripts\python.exe -m src.database update jeteed --source TG --limit 1000
.\.venv312\Scripts\python.exe -m src.database login --source TG
```

`login` без `--source` также обходит все зарегистрированные источники;
`login --source TG` авторизует только Telegram. Аргумент `--resources-file`
задаёт файл со списком ресурсов. Адреса из командной строки и
файла передаются каждому выбранному адаптеру. Каждый адаптер нормализует их отдельно,
после чего дубликаты удаляются. Ошибка адреса или настроек одного источника не мешает
запуску остальных. При этом команда завершается с ошибкой после обхода всех источников,
чтобы частично выполненный запуск не выглядел полностью успешным.

Один `CollectionOptions.as_of` задаёт окно дат на весь запуск. Модель векторизации
загружается один раз и используется всеми выбранными источниками. Для каждого
источника открываются своё подключение к БД и свой клиент; клиент повторно используется
для всех его ресурсов.

`--report` всегда сохраняет один формат JSON, даже при выборе одного источника:
`selected_sources` — список выбранных источников, `sources` — отчёты отдельных
источников, `resources` — их объединённые результаты, `limit_per_resource` — лимит.
Каждый отчёт источника содержит `source`, `resources`, `limit_per_resource` и статус.
Каждая запись ресурса содержит `address`, `source`, `resource` (метаданные), `window`,
счётчики `CollectionResult`, `details` и статус. Имена `channels`, `channel` и
`limit_per_channel` больше не создаются. Показатели Telegram читаются из `details`.
При ошибке сохраняются доступные счётчики и отчёт со статусом `failed`, включая
ошибки создания клиента или подключения к БД. Остальные источники продолжают работу.
При явной отмене статус — `cancelled`, запуск останавливается.

Офлайн-проверка расширения вторым тестовым источником и закрытия соединений:
`python -m unittest model_tests.test_collection_service model_tests.test_collection -v`.

Регрессии разбиения текста, нормализации, отмены подключения и нового формата аудита:
`python -m unittest model_tests.test_embeddings model_tests.test_connection model_tests.test_collection_validation -v`.
Полный набор модульных тестов: `python -m unittest discover -s model_tests -p "test_*.py"`.
Проверка реальной E5 и PostgreSQL после рефакторинга сохранена в
`model_tests/results/database_refactor_check_20261023.json`: 12 сценариев прошли,
временная БД удалена. Рабочие статьи этим запуском не изменялись.

## Запуск

1. Скопируйте `.env.example` в `.env` и задайте `TG_API_ID` и `TG_API_HASH` из [my.telegram.org](https://my.telegram.org). При изменении параметров PostgreSQL обновите также `DATABASE_URL`.
2. Запустите БД: `docker compose up -d db`.
3. Установите зависимости: `python -m pip install -r requirements.txt`.
4. Создайте или обновите схему: `python -m src.database init-db`. При первом создании тома Docker выполнит `src/database/schema.sql` автоматически. Команда добавляет столбец оценки к существующей схеме с UUID и пересчитывает оценки всех сохранённых статей.
5. Войдите в Telegram: `python -m src.database login --source TG`. Команда запросит номер телефона, код входа и, если включена, двухфакторную парольную фразу в локальном терминале. Сессия сохраняется по пути `TG_SESSION`; повторный вход обычно не требуется.
6. Загрузите или обновите канал: `python -m src.database update '@channel_name'`.

PostgreSQL контейнера доступен на `localhost:5433` (внутри контейнера — `5432`). Порт задаётся в `POSTGRES_PORT`; при его изменении обновите порт в `DATABASE_URL`.

`--limit` ограничивает число подходящих текстовых публикаций **для каждого канала**; значение по умолчанию — **1000**. `update` добавляет новые статьи и обновляет текст, категорию, социальные метрики, аудиторию на момент их замера и оценку уже сохранённых статей. При изменении текста пересчитывается вектор. Сообщения без текста или подписи пропускаются и не расходуют лимит.

В `update` обрабатываются только статьи, опубликованные **строго более 48 часов и строго менее 14 дней назад**. Дата публикации берётся из `message.date`; дата редактирования возраст не меняет. Обе границы вычисляются один раз на весь запуск по всем каналам, сравнение выполняется в UTC. Статьи ровно двухдневного или четырнадцатидневного возраста и сообщения без даты не сохраняются. Проверка выполняется до векторизации.

Перед чтением истории `update` удаляет из всей БД статьи, достигшие максимального возраста: по умолчанию **14 дней и старше**. Один SQL-запрос удаляет строки `article_text` по дате публикации; связанные метрики, векторы и связи с источником удаляются через `ON DELETE CASCADE`. Записи самих каналов и статьи без известной даты остаются. Для поиска устаревших записей в схему добавлен индекс по `published_at`; для существующей БД его создаёт повторный `init-db`. При обработке нескольких каналов одного запуска очистка выполняется один раз, даже если подходящих новых сообщений нет. `--max-age-days` задаёт одновременно верхнюю границу сбора и срок хранения. Количество удалённых статей выводится в терминал и сохраняется в поле `deleted_expired` JSON-отчёта; это отдельное число, не входящее в `processed`.

Изолированная проверка удаления: `python -m model_tests.retention_check`. Она проверяет реальные каскады PostgreSQL, границы возраста и повторные обновления без Telegram и нейросети. Проверка создаёт временную БД и удаляет её после завершения; рабочие статьи не меняются.

История запрашивается сразу до границы двух дней через `offset_date`, от новых сообщений к старым. На границе 14 дней просмотр останавливается. Поэтому свежие посты и записи без текста не мешают набрать до 1000 подходящих статей. Если за окно их меньше, сохраняются все доступные. Верхнюю границу можно изменить аргументом `--max-age-days`, большим 2. Общие правила заданы в `BDdataCollection.MIN_ARTICLE_AGE`, `MAX_ARTICLE_AGE` и `is_article_in_window`.

Сбор четырёх каналов одним запуском:

```powershell
.\.venv312\Scripts\python.exe -m src.database update jeteed lol_community khmrchk mknewsru --limit 1000 --max-age-days 14 --report model_tests/results/collection.json
```

В этом запуске модель и сессия Telegram используются повторно для всех каналов. Ресурсы, аудитория и метрики остаются отдельными для каждого канала. Параметр `--report` сохраняет число статей, снимок аудитории и точные границы окна.

## Список проверенных каналов

Редактируемый список источников — [channels.txt](channels.txt). Один адрес на строку; комментарий после `#` служит заметкой и не задаёт тему конкретной статьи. Тема по-прежнему определяется по тексту. В файле исходные четыре канала и 20 дополнительных, проверенных через API на доступность комментариев, реакций, просмотров и аудитории.

```powershell
.\.venv312\Scripts\python.exe -m src.database update --resources-file src/database/channels.txt --limit 1000 --report model_tests/results/all_channels_collection.json
```

Полнота метрик обязательна при каждом `update`: сохраняются только публикации, для которых известны просмотры, реакции, комментарии и положительная аудитория. Просмотры должны быть положительными; нулевые просмотры считаются некорректными данными и пропускаются до векторизации. Нулевые реакции и комментарии допустимы и сохраняются. Неизвестные показатели не заменяются нулями; публикации с ними также пропускаются. Отключить эту проверку нельзя. Лимит 1000 относится к пригодным постам; пропущенные записи не расходуют его. Счётчик пропусков находится в `resources[].details.skipped_incomplete_metrics`.

Можно совместить явные адреса и файл. Если нужно дополнить набор новыми каналами, укажите только новые адреса либо отдельный файл с ними. Команда выполняет UPSERT и сохраняет существующие статьи по их стабильным ID.

Явная очистка пяти таблиц проекта: `python -m src.database reset-db`. Команда сохраняет схему, расширение pgvector и саму базу. Пример полного пересоздания набора: сначала `reset-db`, затем приведённый выше `update`. Очистку следует запускать только для намеренного удаления текущего набора данных.

Повторный `update` находит существующие статьи по стабильному UUID и обновляет их через `ON CONFLICT ... DO UPDATE`. Новая запись создаётся при первом появлении ID статьи. Вывод команды показывает отдельно число добавленных и обновлённых статей, например: `Processed 5736 text posts; added 0; updated 5736`. Для неизменённого текста сохраняется прежний вектор.

## Темы статей

`ArticleTopicDetector` выбирает одну категорию из [topics.txt](topics.txt). Сейчас доступны: Аниме, Игры, Технологии, Кино, Музыка, Мода, Юмор, Знаменитости, Книги, Комиксы, Соцсети, Еда, Искусство и Животные. Название выбранной категории сохраняется в `article_text.topic`.

Чтобы добавить тему, допишите строку в `src/database/topics.txt`:

```text
Спорт | Спортивные соревнования, команды, спортсмены, тренировки и результаты матчей.
```

Можно указать только название (`Спорт`), но описание помогает отличать близкие категории. Пустые строки и комментарии, начинающиеся с `#`, игнорируются. Файл читается при создании коллектора; после изменения списка запустите новую команду `update`.

Модель E5 кодирует описания категорий с префиксом `query:`, а текст статьи — с `passage:`. Категория выбирается по наибольшему косинусному сходству. Единственный метод классификации — `detect_from_embedding(vector)`; готовый вектор статьи передаётся без повторной векторизации текста. Векторы категорий вычисляются при первом обращении и сохраняются в детекторе. При повторной загрузке неизменённой статьи используется её сохранённый вектор; изменение только категории не удаляет этот вектор. После редактирования списка `update` переклассифицирует просматриваемые статьи, включая те, у которых тема раньше была первой строкой публикации.

Всегда выбирается одна из перечисленных тем. Статьи вне этого списка тоже получат ближайшую категорию. Качество такого определения нужно проверить на примерах реальных публикаций после загрузки модели.

## Идентификаторы и таблицы

| Таблица | Содержимое |
| --- | --- |
| `resource` | UUID ресурса, название, число читателей при наличии |
| `article_text` | UUID статьи, тема, полный текст, `published_at` — дата публикации |
| `article_sources` | UUID статьи, UUID ресурса, строковый тип источника (`TG`) |
| `article_metrics` | Просмотры, реакции, комментарии, `audience` — аудитория на момент сбора, `collected_at` — время сбора, `popularity_pattern_score`; `NULL` означает недоступный показатель |
| `article_vectors` | UUID статьи и вектор настроенной размерности (по умолчанию 384) |

`telegram_message_id` в БД отсутствует. `article_id_for(source, external_resource_id, external_article_id)` детерминированно вычисляет UUID статьи по собственным стабильным идентификаторам источника. Коллектор проверяет наличие статьи по этому UUID. Для нового сайта достаточно вызвать ту же функцию с его типом и идентификаторами; схему менять не потребуется. UUID ресурса аналогично вычисляется через `resource_id_for`.

## Векторизация

Модель выбирается через `EMBEDDING_MODEL` в `.env`, размер — через `EMBEDDING_DIMENSIONS`. По умолчанию используется `intfloat/multilingual-e5-small`, 384 компоненты. Префиксы задаются `EMBEDDING_DOCUMENT_PREFIX` / `EMBEDDING_QUERY_PREFIX`. При смене модели или профиля нужны пересчёт векторов и переобучение пары. [Настройка и команды](../../docs/embedding_configuration.md).

Перед обучением и векторным поиском БД проверяется: векторы другой модели или без сведений о модели использовать запрещено, даже если размерность совпадает. Старым векторам при обновлении схемы оставляется `NULL`, поскольку установить их происхождение по самим числам нельзя. Для миграции схемы и пересчёта всех векторов из сохранённых текстов выполните:

```powershell
python -m src.database reembed
```

Команда сохраняет статьи, темы, источники и социальные метрики. Каждый пересчитанный вектор записывается отдельно; при прерывании команду можно повторить. Статьи, изменённые или удалённые во время вычисления, пропускаются, чтобы не сохранить устаревший вектор.

Для будущего RAG: `TextEmbedder.embed_query(question)` создаёт вектор запроса, `ArticleVectorTable.search(vector)` возвращает ближайшие `article_id` по косинусному расстоянию. Схема рассчитана на 384 измерения выбранной модели.

## Оценка популярности

Класс `AssesmentConformPPmetricsBased` учитывает просмотры, реакции, комментарии и аудиторию. Вес просмотров — 20%, реакций — 40%, комментариев — 40%. При сборе аудитория сохраняется вместе с соответствующими метриками в `article_metrics.audience`. При `init-db` оценки пересчитываются по этому снимку. Изменение `resource.reader_count` после роста канала не меняет основу ранее собранных оценок. При новом сборе статьи её метрики и снимок аудитории обновляются вместе. Неизвестная аудитория не подменяется старым значением из `resource`; оценка остаётся `NULL`. Формула описана в [ReadMe модуля оценки](../assesment_conform_of_PP_metric_based/ReadMe.md).

Окно 14 дней уменьшает расхождение между аудиторией при публикации и при сборе. Telegram предоставляет текущую аудиторию; сохранённый снимок не является исторической аудиторией точно в момент публикации. Старые строки без снимка нельзя достоверно пересчитать по сегодняшнему числу подписчиков — их нужно собрать заново. Текущий набор был очищен и собран по новому правилу.

Если том БД уже содержит прежнюю схему с числовыми ID и `telegram_message_id`, `init-db` выдаст ошибку вместо удаления данных. Эти данные потребуется отдельно мигрировать; чистый том создаётся сразу с новой схемой.

Офлайн-проверка логики: `python -m unittest discover -s model_tests -v`. Все тесты находятся вне `src`.

Проверка с реальными PostgreSQL и моделью E5: `python -m model_tests.integration_check`. Требуются запущенная БД и установленные зависимости. Проверка создаёт отдельную временную БД, заполняет все пять таблиц контрольными публикациями, проверяет обновление данных, поиск по векторам и откат при ошибке. Telegram API в этой проверке заменён контрольными ответами; реальное получение публикаций проверяется отдельно командой `update`. Временная БД удаляется после проверки, отчёт сохраняется в `model_tests/results/database_integration_report.json`. Пользователь PostgreSQL должен иметь право создавать временные базы.

Проверка реального сбора: `python -m model_tests.live_telegram_check '@channel_name' --limit 10`. Она сохраняет публикации в настроенной БД, повторяет сбор через `update`, проверяет связанные записи во всех таблицах, темы, векторы и формулу оценки. Перед запуском выполните `python -m src.database login --source TG`. Отчёт — `model_tests/results/telegram_database_report.json`. В PowerShell имя канала с `@` передавайте в кавычках.

В Windows команды модуля используют `SelectorEventLoop`, совместимый с асинхронным драйвером Psycopg. `HF_HOME` в `.env` задаёт каталог кэша скачанной модели; значение из примера — `.cache/huggingface`.

## Пересчёт оценок

`ArticleMetricTable.recalculate_scores()` читает сохранённые социальные метрики и аудиторию наблюдения, вызывает `AssesmentConformPPmetricsBased.assess()` и записывает результат. Операция выполняется в одной транзакции с блокировкой выбранных строк; при ошибке пересчёт полностью откатывается. Модуль оценки не обращается к БД.

Telegram-классы импортируются из места реализации: `from src.database.resources.telegram.collector import TGdataCollection, reaction_count`. Динамические экспорты через `__getattr__` удалены.

## Обучение оценки по тексту

Третий модуль — `src/assesment_conform_of_PP_text_based`. `ArticleTextTable.list_training_data()` отдаёт ему текст, тему, оценку по метрикам и сохранённый вектор. Обучение и прогноз описаны в [ReadMe третьего модуля](../assesment_conform_of_PP_text_based/ReadMe.md); сравнение четырёх моделей по MSE и времени находится в `model_tests/compare_text_models.py`.

Текущая формула метрик — `log-activity-v3`: сначала объединяются взвешенные `ln(1 + метрика / опора)`, затем общий показатель переводится через логарифм и `tanh` в шкалу −10…10. Опорные доли — 10% просмотров, 0,08% реакций и 0,005% комментариев от аудитории. Нули реакций/комментариев больше не дают отдельного фиксированного штрафа. Нулевые просмотры или аудитория исключают оценку. `init-db` пересчитывает сохранённые оценки; после смены версии необходимо переобучить согласованную пару модулей 3/4.
