# Корректировка текста — модуль 5

Вход: исходный текст и похожие статьи с высокой оценкой соответствия паттернам популярности. Выход: JSON с рекомендациями и одним вариантом переписывания **для каждого предложения**, а также собранным новым текстом.

```text
Исходный текст + тема (необязательна)
                    ↓
SearchSimillar → PostgreSQL / pgvector → популярные похожие статьи
                    ↓
LLManalysis → подбор количества примеров под контекст → OpenRouter
                    ↓
Проверка JSON, предложений и ссылок на примеры → результат JSON
```

## SearchSimillar

Использует ту же `intfloat/multilingual-e5-small` и сохранённые векторы, что модуль БД. Полный исходный текст векторизуется как документ; длинные тексты обрабатываются общим `TextEmbedder` частями. Если тема не передана, определяется через редактируемый `src/database/topics.txt`.

`ArticleVectorTable.search_popular()` сначала отбирает в PostgreSQL статьи с `article_metrics.popularity_pattern_score >= 5` и косинусной близостью текста не ниже `0.6`. Затем берёт 100 ближайших по тексту кандидатов. Используется наблюдаемая оценка **модуля 2**, сохранённая в БД.

`SearchSimillar` уточняет порядок:

```text
rank = 0.80 × cosine(текст, текст примера)
     + 0.15 × cosine(эмбеддинг темы, эмбеддинг темы примера)
     + 0.05 × (оценка популярности + 10) / 20
```

Сходство текста имеет больший вес, чем два остальных сигнала вместе. Темы сравниваются семантически через E5 и кэшируются. Одинаковые нормализованные тексты и копия исходной статьи исключаются. `--exclude-article-id` дополнительно исключает статью по UUID. Пороги и веса можно изменить; веса обязаны сохранять приоритет текста.

Если после исключения копий не осталось похожих по содержанию статей, выполняется резервный поиск: выбираются лучшие статьи **строго выбранной темы**, по убыванию наблюдаемой оценки модуля 2. Для этого режима нет порога близости текста и порога оценки 5: используются лучшие доступные примеры темы, в том числе с более низкими оценками. Примеры без сохранённого вектора тоже доступны; их `text_similarity` равен `null`.

В JSON `retrieval.selection_method` равен `content_similarity`, `topic_popularity` или `general`. Каждый пример содержит свой `selection_method`; промпт явно объясняет LLM, что резервные примеры выбраны только по теме и оценке. Они служат ориентирами подачи и структуры, факты из них переносить нельзя.

При резервном подборе возвращается предупреждение **«Похожих по содержанию статей не найдено. Для примеров подобраны лучшие тексты по теме …»**. Оно показывается в UI над карточками ещё во время ожидания LLM, сохраняется вместе с готовыми рекомендациями и остаётся видимым при ошибке API. Если в выбранной теме нет доступных примеров, LLM всё равно вызывается для общих редакторских рекомендаций с дополнительным предупреждением. Недоступность API или непроверенный JSON по-прежнему обрабатываются как ошибки сервиса.

## LLManalysis и контекст

Модель задаётся `OPENROUTER_MODEL` или `--model`. Клиент получает актуальные ограничения из публичного каталога OpenRouter: контекст, предел ответа, поддержку JSON и цены. По умолчанию разрешены **только бесплатные модели**; также в маршрутизации запроса установлен нулевой предел цены.

Количество примеров выбирается автоматически: сначала резервируются инструкции, исходная статья **целиком**, JSON Schema и место для ответа. Затем найденные примеры рассматриваются в порядке ранга и добавляются **только целиком**, без сокращения текста, пробелов и переносов. Если очередной пример не помещается во все запросы анализа, он пропускается; проверяется следующий. Таким образом, при ограничении контекста уменьшается число примеров. По умолчанию CLI использует до 8 примеров; предел можно изменить через `--max-examples` или `.env`. В UI действует `UI_MAX_EXAMPLES=5`: передаются пять полных примеров, если они найдены и помещаются в контекст; значение можно увеличить. Если ни один пример не помещается, LLM даёт общие редакторские рекомендации с предупреждением.

Для независимости от токенизатора поставщика размер считается **с запасом по числу байтов UTF-8** с дополнительным резервом. Это не точный подсчёт токенов провайдера. По умолчанию бюджет входа дополнительно ограничен 24000, ответа — 8192. В JSON возвращаются выбранное количество примеров и использованные бюджеты. Если исходник не помещается даже без примеров, возвращается понятная ошибка; он не обрезается молча.

Предложения выделяет `razdel`; сохраняются ID, начало и конец в Python-символах (индексы с нуля, конец не включён). Для больших ответов предложения анализируются несколькими группами. Каждая группа получает полный исходник и выбранные примеры. Результат выдаётся после успешной проверки всех групп. Пробелы и переносы между предложениями сохраняются при сборке `rewritten_text`.

Системный промпт находится в **`prompts/system.txt`**. Его можно редактировать. В нём заданы требования сохранять смысл, факты, числа, ссылки и авторский стиль, а также использовать примеры как ориентиры подачи. Высокая оценка примера не считается доказательством причин роста популярности.

## Контракт JSON

Для каждого предложения возвращаются:

```json
{
  "sentence_id": 1,
  "start": 0,
  "end": 29,
  "original": "Игроки получат 3 новые карты.",
  "recommendations": [
    {
      "aspect": "clarity",
      "recommendation": "Перенести количество карт в начало фразы.",
      "reason": "Так основное изменение считывается быстрее.",
      "reference_article_ids": []
    }
  ],
  "rewrite": "3 новые карты станут доступны игрокам."
}
```

Верхний объект содержит `topic`, `model`, `references`, `context`, `sentences`, `rewritten_text`, а при полном поиске — `retrieval`. Список `references` включает UUID статей, полный текст примера, тему, оценку популярности, обе близости и итоговый ранг. Поле `truncated` сохранено для совместимости и всегда равно `false`. В `context.examples_skipped_context` записывается число уникальных примеров, пропущенных из-за бюджета контекста; `examples_used` показывает число переданных целых примеров.

Модели с `structured_outputs` получают строгую JSON Schema. Для моделей с обычным `response_format` используется JSON mode и та же схема в промпте. В обоих случаях ответ дополнительно проверяется локально через `jsonschema`: все предложения присутствуют ровно один раз, оригиналы совпадают, рекомендации и переписывание непустые, ссылки ведут только на переданные примеры. Оборванный ответ, Markdown вместо JSON или выдуманные ID не выдаются как готовый результат.

LLM возвращает только `sentence_id`, `recommendations` и `rewrite`. Поля `original`, `start`, `end` формирует сервер из сохранённого исходника: изменения кавычек или пробелов при копировании текста моделью больше не приводят к отказу всего анализа. Публичный JSON результата сохраняет прежние поля.

Если часть предложений не проходит проверку, корректные результаты сохраняются, а проблемные предложения отправляются на **одну** повторную генерацию с описанием нарушения. Повторный ответ проходит те же проверки. В запросе остаётся полный исходный текст; при нехватке контекста удаляются целые примеры. Если повторная проверка не пройдена, возвращается ошибка. `context.validation_repairs` и `context.calls` показывают количество повторных проверок и все завершённые ответы, включая неудачную первую генерацию; их usage учитывается в сумме.

Дополнительно проверяются числовые значения, некоторые числовые ограничения («до», «не менее» и т. п.), URL и превращение сообщения производителя в гарантию. Это консервативные проверки типичных ошибок, **не полная проверка сохранения смысла**. Предложения модели требуют редакторского просмотра.

## Настройка и запуск

Из корня проекта, при запущенной PostgreSQL:

```powershell
.\.venv312\Scripts\python.exe -m pip install -r requirements.txt
```

Добавьте ключ локально в `.env`:

```dotenv
OPENROUTER_API_KEY=ваш_ключ
OPENROUTER_MODEL=nvidia/nemotron-3.5-super-vl:free
OPENROUTER_FREE_ONLY=true
OPENROUTER_MAX_INPUT_TOKENS=24000
OPENROUTER_MAX_OUTPUT_TOKENS=8192
OPENROUTER_TIMEOUT_SECONDS=90
OPENROUTER_RETRIES=2
TEXT_CORRECTION_MAX_EXAMPLES=8
TEXT_CORRECTION_MIN_SCORE=5
```

Доступность бесплатных моделей меняется; проверенные варианты и ошибки находятся в результатах сравнения в `model_tests/results/text_correction_llms_*/`. Модель можно сменить через `.env` или `--model`.

В текущей проверке выбрана `nvidia/nemotron-3.5-super-vl:free`: оба тестовых текста дали полный результат за 20–28 секунд. У неё также наблюдались 502 и таймауты при отдельных запусках CLI. Сводка шести моделей находится в `model_tests/results/text_correction_comparison.md`. `artifacts/text_correction/verified_api_result.json` и `verified_input.txt` содержат сохранённый успешный реальный пример; промпт последнего запуска CLI доступен в `artifacts/text_correction/prepared_request.json`.

```powershell
# Только поиск популярных похожих статей, без вызова LLM
.\.venv312\Scripts\python.exe -m src.text_correction search --text-file model_tests/example_article.txt --topic 'Технологии' --output artifacts/text_correction/search.json

# Посмотреть реальные промпты и выбранные примеры без генерации
.\.venv312\Scripts\python.exe -m src.text_correction correct --text-file model_tests/example_article.txt --prepare-only --output artifacts/text_correction/request.json

# Полный процесс с определением темы и сохранением результата
.\.venv312\Scripts\python.exe -m src.text_correction correct --text-file model_tests/example_article.txt --output artifacts/text_correction/result.json
```

В режиме `--prepare-only` запрашивается только публичный каталог моделей; ключ и генерация не нужны. Если не указан `--output`, JSON печатается в терминал. Ошибки выводятся в stderr в формате JSON, код выхода 2. Файл результата записывается только после полного успешного анализа. Исходные статьи, наблюдаемые оценки и векторы в БД не изменяются.

Клиент учитывает таймаут и ограниченно повторяет ответы 429/временные ошибки сервера с `Retry-After`. В режиме `OPENROUTER_FREE_ONLY=true` при временном сбое, таймауте или незавершённом ответе возможен автоматический переход на резервную модель из `OPENROUTER_FALLBACK_MODELS` (список ID через запятую). По умолчанию это `dots-studio/dots-3-note-preview:free` и `google/gemma-4-26b-a4b-it:free`. Перед генерацией проверяются нулевая цена, поддержка JSON, контекст и выходной бюджет; запрос ограничивает цену нулём. Пустой список отключает резерв. При разрешённых платных запросах автоматический переход не выполняется: зависший запрос мог уже списать средства.

`OPENROUTER_REASONING_ENABLED=false` по умолчанию отключает дополнительные рассуждения у моделей, каталог которых явно разрешает их отключать. Для обязательного или неизвестного режима параметр не переопределяется. Это уменьшает задержку и расход выходного бюджета для редакторской задачи. См. [параметры reasoning OpenRouter](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

В интерфейсе различаются таймаут, ограничение частоты, ошибка ключа, недоступность провайдера и нарушение формата/фактов. Причина пишется в лог сервера без заголовков запроса. Ключ не включается в JSON, промпты, отчёты или отображаемые ошибки.

## Python API

```python
from src.database.connection import connect_database
from src.database.model_embedding import TextEmbedder
from src.database.table_classes import ArticleVectorTable
from src.text_correction import (
    SearchSimillar, LLManalysis, OpenRouterClient, TextCorrectionModule,
)

async def correct(dsn, text):
    async with await connect_database(dsn) as conn, OpenRouterClient() as client:
        search = SearchSimillar(ArticleVectorTable(conn), TextEmbedder())
        analysis = LLManalysis(client, max_examples=8)
        return await TextCorrectionModule(search, analysis).correct(text, topic=None)
```

Перед этим загрузите `.env`. На Windows используйте `asyncio.Runner(loop_factory=asyncio.SelectorEventLoop)` как в CLI проекта. Если примеры уже получены, можно вызвать `await analysis.analyze(text, articles, topic="Игры")` непосредственно; `articles` — список `SimilarArticle`. `prepare()` возвращает промпты без генерации, `execute(plan)` выполняет подготовленный анализ.

## Отдельная проверка языка

`LanguageCheck(client).check(text)` делает отдельные запросы к OpenRouter: орфография,
пунктуация, грамматика и синтаксис. Поиск примеров, БД, тема и модели прогнозирования
для этой проверки не нужны. Используются те же настройки модели и бесплатных резервов.
Инструкции находятся в `prompts/language_check.txt`.

Модель возвращает ID предложений и слов, исправления и объяснения. Координаты берёт
сервер из исходного текста, а не из ответа LLM. `issues` содержит `kind`, `original`,
`rewrite`, `explanation`, диапазон подсветки и отдельные `edits`. Для орфографии
подсвечивается слово, для пунктуации, грамматики и синтаксиса — предложение целиком.
Пунктуационные изменения выделяются относительно текста с уже исправленной
орфографией: их принятие не возвращает ошибочное написание слова. Числа, ссылки
и числовые оговорки проверяются; некорректный ответ повторяется один раз и затем
отклоняется. Корректные результаты сохраняются, повторно отправляются только
проблемные предложения. Если часть предложений не прошла проверку и со второго
раза, возвращаются доступные правки, `unchecked_sentences` и видимое предупреждение
о частичной проверке. Такой результат не означает, что в остальных предложениях
ошибок нет. Если не подтверждено ни одно предложение, возвращается ошибка.
Составные слова с цифрами и дефисом проверяются как целые токены; изменения
числовых фактов по-прежнему запрещены. Замены без изменения написания игнорируются,
стилистическая замена прямых кавычек на ёлочки не считается языковой ошибкой.
Отсутствие найденных ошибок в полностью проверенном тексте возвращает пустой `issues`.

Проверка языковой моделью не гарантирует обнаружение всех ошибок. Изменения
применяются только после принятия пользователем.

## Проверки и сравнение бесплатных моделей

Весь тестовый код находится вне `src`, в `model_tests`:

```powershell
.\.venv312\Scripts\python.exe -m unittest model_tests.test_text_correction -v
.\.venv312\Scripts\python.exe -m model_tests.compare_text_correction_llms
```

Сравниваются реальные API-запросы на двух одинаковых текстах с одинаковыми найденными примерами. Сохраняются JSON-ответы, промпты, время API, покрытие предложений и результаты проверки чисел. Ошибки и недоступность моделей включаются в отчёт. Это формальные проверки и проверка доступности, а не объективная оценка качества литературной правки или роста популярных метрик.
